### What shipped

  plus `PER_YOUTH_FEE = 50` and `SOFT_CAP_PER_PARISH = 15` constants.
- `routes/anubhav.js` — wired 7 new Phase 1 endpoints behind
  `requireEventRole(['loc','dexco']) + requirePlaceAccess` (DELETE uses only
  the role check since URL carries no `place`; the row's place is validated
  inside the controller).

### Endpoints now live (matches API_CONTRACT.md §"Registration (Phase 1)")
- `GET    /anubhav/eligible?place=&deanery=&parish=&search=`
- `POST   /anubhav/chaperones`                         body: `{place,parish,name,phone,type}`
- `GET    /anubhav/chaperones?place=&parish=`
- `POST   /anubhav/registrations`                      body: `{place,profile_id,chaperone_id?}`
- `GET    /anubhav/registrations?place=&deanery=&parish=`
- `DELETE /anubhav/registrations/:id`                  (soft delete, status=0)
- `GET    /anubhav/fees?place=`                        returns `{perYouth, byParish, byDeanery, placeTotal, overall}`

### Design notes
- Soft cap is implemented as a non-blocking `warnings: []` array on the
  registration response, never as a 400. Matches plan §3 "warn, do not block".
- Fee math is sourced from `r.fee_amount` (default 50) so any future per-row
  override is respected; `perYouth` is reported as the literal contract value.
- DELETE is soft (status=0). Because `uniq_place_profile(place, profile_id)`
  only counts `status=1` rows in queries, re-registration works after un-register.
  (Aside: the unique key itself is at the DB level and ignores status — if MySQL
  enforces it strictly on insert, we'll need a hard delete instead; revisit if
  re-registration ever returns ER_DUP_ENTRY.)
- Allotment cleanup happens before registration soft-delete, because
  `anubhav_allotments.registration_id` is a non-cascading FK.
